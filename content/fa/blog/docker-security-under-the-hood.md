# مقدمه

امنیت کانتینرها در دههٔ گذشته پیشرفت چشمگیری داشته، اما توصیه‌های مرتبط با آن هنوز به اندازهٔ کافی عمیق و مفهومی ارائه نشده‌اند.

اگر «بست پرکتیس داکر» را جستجو کنید، احتمالاً با توصیه‌هایی مثل این مواجه می‌شوید:

- به‌عنوان کاربر root اجرا نکنید.
- فایل‌سیستم را read-only کنید.
- seccomp را فعال کنید.
- هرگز کانتینر را با حالت privileged اجرا نکنید.

این توصیه‌ها عالی و قابل اجرا هستند، اما اغلب به شکل «قانون» ارائه می‌شوند نه «مفهوم». هدف این مقاله این است که پشت این قوانین را باز کند و مکانیسم‌های امنیتی لینوکس را که در پس آن‌ها قرار دارند، به‌طور کامل توضیح دهد.

این پست بر پایهٔ [OWASP داکر Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html) بنا شده و با توضیح «چرا» این توصیه‌ها مهم هستند و چه حملاتی را دفع می‌کنند، آن را تکمیل می‌کند.

# مدل تهدید (Threat Model)

قبل از هر چیز باید بپرسیم: در مقابل چه کسی دفاع می‌کنیم؟

امنیت کانتینری در ماشین توسعه با محیط تولید عمومی کاملاً متفاوت است.

در این مقاله فرض می‌کنیم:

- برنامه داخل کانتینر در محیط تولید اجرا می‌شود.
- برنامه از طریق شبکهٔ غیرمطمئن در معرض کاربران ناشناس قرار دارد.
- به‌دلیل وجود آسیب‌پذیری، مهاجم موفق به کسب Remote Code Execution (RCE) داخل کانتینر شده است.
- مهاجم حالا می‌تواند دستورات دلخواه را با privileges همان فرآیند برنامه اجرا کند.

در این سناریو، داکر شکست نخورده؛ بلکه اینجا ویژگی‌های امنیتی runtime داکر شروع به درخشیدن می‌کنند. جلوگیری از آسیب‌پذیری‌هایی مثل SQL injection، command injection یا insecure deserialization وظیفهٔ داکر نیست؛ وظیفهٔ توسعه‌دهنده است.

اهداف مهاجم می‌تواند این باشد:

- خواندن داده‌های حساس مثل API key، credentialها و secrets
- تغییر برنامه یا کانفیگ آن
- حفظ ماندگاری (persistence) و زنده ماندن پس از restart کانتینر
- افزایش privilege داخل کانتینر
- فرار از کانتینر و نفوذ به هاست
- دسترسی به کانتینرهای دیگر در شبکه
- مصرف بیش از حد منابع و ایجاد حملهٔ denial of service

هدف این ویژگی‌های امنیتی محدود کردن مهاجم بعد از نفوذ موفق است. هرکدام از این اهداف باید دشوار یا حتی غیرممکن شوند.

## مثال واقعی

هر سال آسیب‌پذیری‌های RCE در برنامه‌های کانتینرشده کشف می‌شود. مثلاً آسیب‌پذیری React Server Component در سال ۲۰۲۵ ([CVE-2025-55182](https://nvd.nist.gov/vuln/detail/CVE-2025-55182)). این یک vulnerability در React بود، اما برنامه‌های Next.js را تحت تأثیر قرار داد و مهاجمان می‌توانستند با یک HTTP request مخرب، کد دلخواه روی سرور اجرا کنند.

حالا فرض کنید برنامهٔ شما توی یک داکر container اجرا می‌شود و از نسخهٔ آسیب‌پذیر Next.js استفاده می‌کند. مهاجم می‌تواند کد مخرب داخل کانتینر شما اجرا کند.

حالا از خودتان بپرسید:

- آیا می‌توانند برنامهٔ شما را تغییر دهند؟
- آیا می‌توانند secrets را بدزدند؟
- آیا می‌توانند persistence ایجاد کنند؟
- آیا می‌توانند به کانتینرهای دیگر دسترسی پیدا کنند؟
- آیا می‌توانند به هاست فرار کنند؟
- آیا می‌توانند منابع هاست را مصرف کنند؟

اینها همان سؤالاتی هستند که ویژگی‌های امنیتی داکر در این مقاله به آن‌ها پاسخ می‌دهند.

در این زنجیره، داکر از لایهٔ داکر انجین به بالا مسئولیت دارد: چرخهٔ حیات کانتینرها، namespaceها، capabilityها، پروفایل‌های seccomp، LSMها و cgroupها.

**اما هیچ مرزی در برابر خود کرنل لینوکس ایجاد نمی‌کند.** کرنل بین تمام کانتینرها به اشتراک گذاشته شده است. داکر مکانیسم‌های امنیتی کرنل را پیکربندی می‌کند، اما لایهٔ جدیدی برای امنیت روی آن‌ها نمی‌افزاید.

اگر یک vulnerability در زیرسیستم‌های کرنل مثل `OverlayFS`، `eBPF` یا `io_uring` وجود داشته باشد، مهاجم می‌تواند ایزوله‌سازی داکر را دور بزند. این‌ها باگ‌های کرنل هستند، نه اشتباه در پیکربندی داکر. بسیاری از فرارهای مهم کانتینر در سال‌های اخیر ناشی از vulnerabilityهای کرنل بوده‌اند، نه تنظیمات اشتباه داکر. مثلاً [CVE-2023-0386](https://nvd.nist.gov/vuln/detail/CVE-2023-0386) یک فرار از کانتینر بود که با سوءاستفاده از OverlayFS انجام شد و به مهاجم اجازه می‌داد از طریق یک filesystem مخرب مانت‌شده داخل کانتینر، به روت هاست برسد.

این یعنی داکر ناامن نیست. یعنی امنیت کانتینر در نهایت همان امنیت لینوکس است. در ادامهٔ این مقاله دربارهٔ mitigationهایی صحبت می‌کنیم که تأثیر کانتینرهای نفوذی را کاهش می‌دهند.

# اجرای کانتینر به‌عنوان کاربر غیر-root

رایج‌ترین توصیهٔ امنیتی: به‌عنوان root اجرا نکنید.

این توصیهٔ خوبی است، اما اغلب اشتباه درک می‌شود. سؤال این است: اگر کانتینرها ایزوله هستند، پس چرا فرق می‌کند که برنامه به‌عنوان root اجرا شود یا نه؟

پاسخ کوتاه: حتی اگر root داخل کانتینر با root هاست یکی نباشد، همچنان پرامتیازترین کاربر داخل همان کانتینر است. درک این privilegeها کلید فهم این است که چرا اجرا به‌عنوان non-root یک اقدام اساسی برای مقاوم‌سازی کانتینر است.

## Root داخل کانتینر با root هاست یکی نیست

در یک Linux سنتی، کاربر root (UID 0) دسترسی نامحدود به تقریباً همهٔ بخش‌های سیستم‌عامل دارد. اما مدل امنیتی کانتینرها این را تغییر می‌دهد. برخلاف سیستم سنتی، UID 0 داخل کانتینر به معنی کنترل نامحدود روی هاست نیست؛ یعنی کاربر فقط داخل namespace همان کانتینر root محسوب می‌شود.

مثلاً یک پردازهٔ root داخل داکر نمی‌تواند هیچ‌کدام از این کارها را انجام دهد:

- بارگذاری ماژول کرنل
- mount کردن filesystem
- تغییر پارامترهای کرنل
- تغییر ساعت سیستم
- دیدن یا کنترل پردازه‌های خارج از کانتینر یا هاست

این عملیات نیازمند privilegeهایی هستند که داکر عمداً از root داخل کانتینر سلب کرده است. اما حتی با این محدودیت‌ها، root همچنان پرامتیازترین کاربر داخل کانتینر است.

## چرا Kubernetes `runAsNonRoot` را توصیه می‌کند

اگر تا حالا روی Kubernetes برنامه deploy کرده باشید، احتمالاً این تنظیم را دیده‌اید:

```yaml
securityContext:
	runAsNonRoot: true
```

این تنظیم به Kubelet می‌گوید که مطمئن شود کانتینرها با UID 0 شروع نمی‌شوند. اگر image طوری تنظیم شده باشد که به‌عنوان root اجرا شود، Kubernetes از اجرای کانتینر جلوگیری می‌کند. دلیلش بی‌اعتمادی به ایزوله‌سازی داکر نیست. اکثر برنامه‌ها برای سرویس‌دهی HTTP، پردازش job یا تعامل با دیتابیس اصلاً به root نیاز ندارند.

## فرار از کانتینر و چرایی اهمیت آن

اگرچه نادر است، گاهی vulnerability در کرنل لینوکس منجر به فرار از کانتینر می‌شود و به مهاجم اجازه می‌دهد کد روی هاست اجرا کند. یکی از معروف‌ترین نمونه‌ها [CVE-2019-5736](https://unit42.paloaltonetworks.com/breaking-docker-via-runc-explaining-cve-2019-5736/) بود که به یک کاربر root داخل کانتینر اجازه می‌داد با جایگزینی باینری runC هاست (همان runtime کانتینر داکر)، از کانتینر فرار کند.

توجه کنید که اجرای برنامه به‌عنوان کاربر non-root از فرار از کانتینر جلوگیری نمی‌کند، اما سطح حمله و privilege مهاجم را کاهش می‌دهد و کار را دشوارتر می‌کند. این نوع حمله با دور زدن پیکربندی داکر انجام نمی‌شود، بلکه ناشی از vulnerability در خود کرنل است.

## User Namespaces

قبلاً گفتیم که root داخل کانتینر با root هاست فرق دارد. این جداسازی به‌لطف ویژگی‌ای در کرنل لینوکس به نام user namespace امکان‌پذیر است. این ویژگی UID و GID را بین کانتینر و هاست نگاشت می‌کند. مثلاً یک پردازه با UID 0 داخل کانتینر، روی هاست با UID 100000 شناخته می‌شود.

نحوهٔ نگاشت:

| Inside Container | On the Host |
| ---------------- | ----------- |
| UID 0 (root)     | UID 100000  |
| UID 1            | UID 100001  |
| UID 1000         | UID 101000  |

یعنی حتی اگر root کانتینر بخواهد به فایلی که متعلق به root هاست است دسترسی پیدا کند، ناموفق خواهد بود، چون از دید کرنل، کاربر کانتینر root نیست.

User namespaces قدرتمند هستند اما در بسیاری از نصب‌های داکر به‌طور پیش‌فرض فعال نیستند. دلیل اصلی سازگاری است: bind mountها، نگاشت ownership فایل و بعضی storage backendها با نگاشت UID رفتار متفاوتی دارند. بعضی imageها فرض می‌کنند می‌توانند به‌عنوان root فایل بنویسند و آن فایل روی هاست هم متعلق به root باشد — این فرض در user namespace remapping نقض می‌شود. این مشکلات قابل حل هستند، اما نیاز به پیکربندی و آزمایش دارند.

برای محیط‌های تولید با الزامات امنیتی بالا، فعال‌سازی user namespaces باید اولویت باشد. حفاظتی که در برابر تأثیر فرار از کانتینر ایجاد می‌کند به‌سختی با هر مکانیسم دیگری قابل دستیابی است.

# Linux Capabilities

اگر اجرا به‌عنوان کاربر non-root اولین قدم کاهش privileges است، Linux capabilities گام دوم هستند.

در واقع، حتی اگر برنامهٔ شما به‌عنوان root داخل کانتینر اجرا شود، باز هم privilegeهای root در یک Linux سنتی را ندارد. چون Linux مدرن دیگر root را به‌صورت همه‌یاهیچ در نظر نمی‌گیرد. در عوض، عملیات ممتاز را به مجموعه‌ای از قابلیت‌های مجزا (capabilities) تفکیک کرده است.

## چرا Linux root را به Capabilities تقسیم کرد

از نظر تاریخی، Unix فقط دو سطح privilege داشت: یا کاربر root (UID 0) با دسترسی نامحدود، یا کاربر معمولی با محدودیت. این مدل هرچند ساده بود، اما بیش از حد درشتدانه (coarse-grained) بود. Nginx را در نظر بگیرید. اگر Nginx بخواهد به پورت ۸۰ یا ۴۴۳ متصل شود، نیاز به root دارد. اما اعطای تمام دسترسی‌های root به Nginx ضروری نیست. Nginx نیازی به بارگذاری ماژول‌های کرنل یا راه‌اندازی مجدد سیستم ندارد. با مدل سنتی، Nginx با دسترسی root قدرتی فراتر از نیازش می‌گرفت.

Linux capabilities راه‌حل این مشکل هستند. Privilegeهای root را به مجوزهای مجزا تفکیک می‌کنند که هرکدام یک عملیات خاص را مجاز می‌شمارند.

مثال‌هایی از capabilities رایج:

| Capability             | کاربرد                                                              |
| ---------------------- | ------------------------------------------------------------------- |
| `CAP_NET_BIND_SERVICE` | اتصال به پورت‌های زیر ۱۰۲۴                                         |
| `CAP_NET_ADMIN`        | پیکربندی رابط‌های شبکه، جدول‌های مسیریابی، قوانین فایروال و...     |
| `CAP_SYS_PTRACE`       | ردیابی یا دیباگ سایر پردازه‌ها                                      |
| `CAP_SYS_MODULE`       | بارگذاری و تخلیهٔ ماژول‌های کرنل                                    |
| `CAP_SYS_TIME`         | تغییر ساعت سیستم                                                    |
| `CAP_SYS_ADMIN`        | انجام طیف وسیعی از عملیات مدیریتی                                   |

## مجموعهٔ پیش‌فرض داکر

وقتی کانتینر را شروع می‌کنید، داکر خودش تعدادی از capabilityهای خطرناک را حذف کرده است. می‌توانید capabilityهای پیش‌فرض داکر را داخل کانتینر بررسی کنید:

```bash
docker run --rm alpine sh -c "
apk add --no-cache libcap >/dev/null
capsh --print
"
```

خروجی:

![Default capabilities](/images/blog/docker-security-under-the-hood/default-docker-capabilities.png)

می‌بینید که capabilityهایی مثل `CAP_SYS_MODULE`، `CAP_SYS_BOOT`، `CAP_SYS_ADMIN` و `CAP_SYS_TIME` حضور ندارند. به همین دلیل است که یک پردازهٔ root داخل کانتینر پیش‌فرض داکر نمی‌تواند بیشتر کارهایی که root هاست می‌تواند انجام دهد.

## حذف Capabilities با `--cap-drop`

اگر حتی مجموعهٔ پیش‌فرض داکر بیشتر از نیاز برنامهٔ شماست، می‌توانید بیشتر حذف کنید. پرچم `--cap-drop` به شما اجازه می‌دهد capabilityهای مشخص یا همهٔ آن‌ها را یکباره حذف کنید.

```bash
docker run --cap-drop ALL nginx
```

در داکر Compose:

```yaml
services:
  nginx:
    image: nginx:latest
    cap_drop:
      - ALL
```

این تضمین می‌کند کانتینر با حداقل privileges ممکن شروع کند.

## افزودن Capabilities با `--cap-add`

فرض کنید می‌خواهید capability خاصی مثل `CAP_NET_BIND_SERVICE` را برای Nginx فعال کنید تا روی پورت ۸۰ یا ۴۴۳ سرویس دهد. به‌جای دادن دسترسی‌های گسترده، فقط آن capability را اضافه کنید:

```bash
docker run \
--cap-drop ALL \
--cap-add NET_BIND_SERVICE \
nginx
```

در داکر Compose:

```yaml
services:
  nginx:
    image: nginx:latest
    cap_drop:
      - ALL
    cap_add:
      - NET_BIND_SERVICE
```

این روش خیلی امن‌تر از فعال‌سازی همهٔ capabilities است.

## چرا `CAP_SYS_ADMIN` ریشهٔ جدید است

بین همهٔ Linux capabilities، یکی برجسته است: `CAP_SYS_ADMIN`. اگر مستندات کرنل یا advisoryهای امنیتی را خوانده باشید، احتمالاً این جمله را دیده‌اید:

>`CAP_SYS_ADMIN` is the new root.

برخلاف بقیهٔ capabilities که یک عملیات خاص را مجاز می‌کنند، `CAP_SYS_ADMIN` کلی عملیات مدیریتی که لزوماً به هم ربط ندارند را مجاز می‌کند. پردازه‌های با این capability می‌توانند:

- Filesystem را mount و unmount کنند
- عملیات namespace انجام دهند
- بعضی interfaceهای کرنل را پیکربندی کنند
- عملیات filesystem ممتاز انجام دهند
- با eBPF و سایر ویژگی‌های پیشرفتهٔ کرنل تعامل داشته باشند (بسته به نسخهٔ کرنل)

در طول سال‌ها، بسیاری از vulnerabilityها و فرارهای کانتینر سعی در کسب این capability داشته‌اند. اگر برنامهٔ شما به آن نیاز ندارد، اضافه نکنید. به همین سادگی.

## `CAP_NET_ADMIN`: قدرتمندتر از آنچه به نظر می‌رسد

یکی دیگه که مردم اشتباه می‌کنند `CAP_NET_ADMIN` است. با وجود اسمش، فقط دربارهٔ مدیریت شبکه نیست. خیلی بیشتر از آن است.

با این capability می‌توانید:

- رابط‌های شبکه را ایجاد یا تغییر دهید
- جدول‌های مسیریابی را پیکربندی کنید
- قوانین فایروال را مدیریت کنید
- packet forwarding را فعال کنید
- namespace شبکه را تغییر دهید
- traffic control (tc) را پیکربندی کنید

این خوب است اگر VPN server، CNI plugin یا چیزی شبیه این اجرا می‌کنید. اما برای یک برنامهٔ وب معمولی که فقط HTTP سرویس می‌دهد؟ نیاز ندارید. دادن `CAP_NET_ADMIN` به چنین برنامه‌ای فقط به مهاجم گزینه‌های بیشتر می‌دهد.

# Privileged Containers

`--privileged` یک capability نیست. یک flag است که می‌گوید «همه چیز را بده»: تقریباً همهٔ Linux capabilities، دسترسی به deviceهای هاست، محدودیت‌های cgroup سهل‌گیرانه، غیرفعال‌سازی مکانیسم‌های ایمنی.

مردم از آن به‌عنوان میانبر عیب‌یابی استفاده می‌کنند: چیزی کار نمی‌کند، می‌زنند `--privileged` و ادامه می‌دهند. در عوض، بفهمید واقعاً به چه چیزی نیاز دارید: یک capability خاص؟ دسترسی به `/dev/net/tun`؟ دادن یک permission همیشه بهتر از دادن همه چیز است. `--privileged` را برای ابزارهای زیرساختی سطح پایین مثل container runtimeها یا ابزارهای دیباگ نگه دارید، نه برای web app، API یا workerهای پس‌زمینه.

# Read-Only Filesystems

پیش‌فرض، filesystem ریشهٔ کانتینر قابل نوشتن است. پس هر پردازه‌ای داخل آن، از جمله پردازه‌ای که مهاجم کنترل می‌کند، می‌تواند هر جا که مجوزها اجازه می‌دهد فایل ایجاد، تغییر یا حذف کند.

برای خیلی از برنامه‌ها این لازم نیست. یک web server کد را می‌خواند، به درخواست‌ها جواب می‌دهد، شاید لاگ یا کش بنویسد. به ندرت نیاز به تغییر باینری‌های خودش پیدا می‌کند.

داکر به شما اجازه می‌دهد filesystem ریشه را به‌صورت read-only mount کنید.

**داکر:**
```bash
docker run --read-only nginx
```

**داکر Compose:**
```yaml
services:
  app:
    image: my-app:latest
    read_only: true
```

**Kubernetes:**
```yaml
securityContext:
  readOnlyRootFilesystem: true
```

با این کار، هر تلاشی برای تغییر فایل‌های کانتینر ناموفق می‌شود. حتی اگر پردازه مجوز write داشته باشد. محیط کانتینر immutable می‌شود.

این جلوی یک دسته کامل از تکنیک‌های پس از بهره‌برداری که به تغییر filesystem وابسته هستند را می‌گیرد. بدون دسترسی write، مهاجم نمی‌تواند باینری برنامه را با نسخهٔ دردار عوض کند، فایل‌های کانفیگ را برای غیرفعال کردن کنترل‌های امنیتی دستکاری کند، یا مکانیسم‌های persistence مثل cron job، systemd service یا اسکریپت‌های راه‌اندازی نصب کند. نمی‌تواند بدافزار روی دیسک دانلود کند، web shell در ریشهٔ document بگذارد، یا libraryهای اشتراکی را برای LD_PRELOAD-style hijacking بازنویسی کند. حتی با full code execution، مهاجم نمی‌تواند وضعیت کانتینر را به‌طور دائمی تغییر دهد. هر تغییری با restart کانتینر از بین می‌رود.

## ذخیره‌سازی موقت با `tmpfs`

البته بیشتر برنامه‌ها جایی برای نوشتن موقت نیاز دارند: مثل `/tmp`، سوکت‌های runtime، فایل‌های PID، آپلودها، کش‌ها.

به‌جای writable کردن کل filesystem، داکر به شما اجازه می‌دهد مسیرهای مشخصی را به‌صورت `tmpfs` (در حافظه) mount کنید.

**داکر:**
```bash
docker run --read-only --tmpfs /tmp my-nextjs-app:latest
```

**داکر Compose:**
```yaml
services:
  nextjs:
    image: my-nextjs-app:latest
    read_only: true
    tmpfs:
      - /tmp
```

**Kubernetes:**
```yaml
volumes:
  - name: tmp
    emptyDir:
      medium: Memory

containers:
  - name: nextjs
    volumeMounts:
      - name: tmp
        mountPath: /tmp
```

یک mount `tmpfs` در حافظه است. هر چیزی که آنجا نوشته شود با توقف کانتینر از بین می‌رود. پس برنامه فضای موقت خودش را دارد بدون اینکه تغییرات دائمی ممکن باشد.

## مسیرهای writable باید explicit باشند

یک مزیت بزرگ read-only filesystem این است که شما را مجبور به فکر کردن می‌کند: برنامهٔ من واقعاً کجا نیاز به نوشتن دارد؟ به‌جای اجازهٔ نوشتن در همه جا، چند جای محدود را مشخص می‌کنید.

مثلاً:

- `/tmp` برای فایل‌های موقت
- `/var/log` اگر لاگ روی دیسک می‌نویسید
- `/uploads` برای محتوای آپلودی کاربر

بقیهٔ چیزها immutable می‌مانند. این سطح حمله را به میزان قابل توجهی کاهش می‌دهد.

## Read-Only Filesystem جلوی چه چیزهایی را نمی‌گیرد

یک read-only root filesystem فقط نوشتن روی دیسک را مسدود می‌کند. جلوی اکسپلویت اولیه را نمی‌گیرد، جلوی اجرای کد را نمی‌گیرد، و محدودیتی برای کار در حافظه ایجاد نمی‌کند. مهاجم با RCE همچنان می‌تواند داده خارج کند، reverse shell بزند، به سرویس‌های دیگر حمله کند یا از interfaceهای کرنل سوءاستفاده کند — تا وقتی که این کارها نیاز به نوشتن روی دیسک نداشته باشند.

مثلاً [Sysdig مستند کرده](https://www.sysdig.com/blog/containers-read-only-fileless-malware) که مهاجمان چطور از filesystemهای مبتنی بر حافظه مثل `/dev/shm` برای دانلود و اجرای بدافزار کاملاً در RAM استفاده می‌کنند، بدون اینکه اثری روی دیسک باقی بماند. این تکنیک که fileless malware نام دارد، محدودیت‌های read-only filesystem را کاملاً دور می‌زند. بدافزار اجرا می‌شود، آسیب می‌زند، و با توقف کانتینر ناپدید می‌شود — هیچ فایلی هرگز لمس نشده.

# جلوگیری از Privilege Escalation با `no-new-privileges`

تا اینجا دربارهٔ کاهش privilegeهایی که کانتینر با آن شروع می‌کند صحبت کردیم. اما اگر پردازه بعد از اجرا تلاش کند privilege بیشتری کسب کند چه؟

در Linux راه‌هایی برای این کار وجود دارد. رایج‌ترین‌شان باینری‌های setuid و file capabilities هستند.

کرنل یک ویژگی به نام No New Privileges (NNP) دارد که جلوی این را می‌گیرد.

**داکر:**
```bash
docker run --security-opt no-new-privileges:true my-app:latest
```

**داکر Compose:**
```yaml
services:
  app:
    image: my-app:latest
    security_opt:
      - no-new-privileges:true
```

**Kubernetes:**
```yaml
securityContext:
  allowPrivilegeEscalation: false
```

وقتی این فعال باشد، کرنل تضمین می‌کند که پردازه نمی‌تواند privilegeای بیشتر از آنچه از ابتدا داشته کسب کند. مهم نیست چه برنامه‌ای اجرا کند. این یکی از ساده‌ترین و مؤثرترین کارهایی است که می‌توانید انجام دهید.

## درک `setuid`

فایل‌های Linux می‌توانند یک permission خاص به نام `setuid` داشته باشند. معمولاً یک برنامه با privilegeهای شخصی که آن را اجرا می‌کند اجرا می‌شود. اما یک برنامهٔ setuid با privilegeهای مالک فایل اجرا می‌شود.

ابزار `passwd` را در نظر بگیرید. باید `/etc/shadow` را تغییر دهد که فقط root می‌تواند در آن بنویسد. به‌جای root کردن همهٔ کاربران، Linux `passwd` را به‌عنوان setuid علامت‌گذاری می‌کند تا موقتاً با privilegeهای root اجرا شود.

این مفید است، اما فرصتی برای privilege escalation هم هست. اگر مهاجم یک باینری setuid آسیب‌پذیر پیدا کند، ممکن است privilegeهایی را که نباید داشته باشد به دست آورد.

با no-new-privileges، کرنل بیت setuid را نادیده می‌گیرد. برنامه هنوز اجرا می‌شود، اما privilege بالایی دریافت نمی‌کند.

## File Capabilities (`setcap`)

Capabilities را می‌توان مستقیماً با `setcap` به فایل‌های اجرایی چسباند:

```bash
setcap cap_net_bind_service=+ep /usr/local/bin/my-server
```

این به باینری اجازه می‌دهد بدون نیاز به root بودن به پورت‌های ممتاز متصل شود. اما با no-new-privileges، این capabilities اضافی در طول اجرا کسب نمی‌شوند.

## مثال: PwnKit

یک مثال واقعی PwnKit ([CVE-2021-4034](https://nvd.nist.gov/vuln/detail/CVE-2021-4034)) است. روی `pkexec` تأثیر می‌گذاشت، یک ابزار setuid-root در اکثر توزیع‌های Linux. یک باگ به هر کاربر local غیرممتاز اجازه می‌داد یک shell روت بگیرد.

حالا برنامهٔ Next.js نفوذی ما را تصور کنید. مهاجم `pkexec` را پیدا می‌کند و سعی می‌کند از آن سوءاستفاده کند.

بدون no-new-privileges، کرنل بیت setuid را احترام می‌گذارد. اگر اکسپلویت کار کند، مهاجم root می‌شود. با no-new-privileges، کرنل از دادن privilege اضافی خودداری می‌کند. مهاجم می‌تواند `pkexec` را اجرا کند، اما با privilegeهای موجود خودش اجرا می‌شود. هیچ privilege escalationی رخ نمی‌دهد.

برای روشن شدن: no-new-privileges یک دفاع جهانی در برابر همهٔ LPEها نیست. این ویژگی به‌طور خاص privilegeهای جدید از طریق setuid و file capabilities را در طول `execve()` مسدود می‌کند.

# Seccomp: محدود کردن فراخوانی‌های سیستمی

حتی بعد از حذف capabilities و جلوگیری از privilege escalation، یک پردازهٔ نفوذی هنوز می‌تواند فراخوانی‌های سیستمی (syscall) انجام دهد.

هر کاری که یک userspace program با کرنل انجام می‌دهد از طریق syscall است. خواندن فایل، باز کردن سوکت، ایجاد پردازه، تخصیص حافظه. همه چیز.

Seccomp به شما کنترل می‌دهد که یک پردازه کدام syscallها را می‌تواند انجام دهد. Linux مدرن صدها syscall دارد. `mount()`، `bpf()`، `ptrace()` — interfaceهای قدرتمند کرنلی که بیشتر برنامه‌ها هرگز نیاز ندارند.

## پروفایل پیش‌فرض Seccomp داکر

داکر یک پروفایل seccomp به‌طور پیش‌فرض به هر کانتینر اعمال می‌کند. syscallهای پرخطر که برنامه‌های معمولی به ندرت نیاز دارند را مسدود می‌کند.

اما نکته اینجاست: پروفایل پیش‌فرض داکر عمداً سهل‌گیرانه (permissive) است. چیزهایی که مشخصاً خطرناک هستند را مسدود می‌کند، اما یک whitelist سختگیرانه نیست. بیشتر syscallها هنوز مجازند. چون پروفایل محدودکننده‌تر پیش‌فرض باعث می‌شود خیلی چیزها بشکند.

در محیط‌های با امنیت بالا، باید پروفایل پیش‌فرض را نقطهٔ شروع در نظر بگیرید، نه پیکربندی نهایی. پروفایل‌های سفارشی که فقط syscallهای مورد استفادهٔ واقعی برنامه را مجاز می‌کنند، خیلی قوی‌تر هستند.

## روش درست پیکربندی Seccomp

داکر به شما اجازه می‌دهد یک پروفایل seccomp سفارشی با `--security-opt` اعمال کنید:

```bash
docker run --security-opt seccomp=/path/to/profile.json my-app
```

پروفایل یک فایل JSON است که مشخص می‌کند کدام syscallها مجاز یا ممنوع هستند. اگر می‌خواهید seccomp را غیرفعال کنید (توصیه نمی‌شود)، از `unconfined` استفاده کنید:

```bash
docker run --security-opt seccomp=unconfined my-app
```

برای ساخت یک پروفایل سفارشی، می‌توانید از ابزارهایی مثل `strace` یا `auditd` برای ضبط syscallهایی که برنامه در طول عملیات عادی انجام می‌دهد استفاده کنید، سپس یک whitelist از روی آن بسازید. [مستندات رسمی داکر](https://docs.docker.com/engine/security/seccomp/) مرجع کاملی برای فرمت پروفایل و مثال‌ها دارد.

**داکر Compose:**
```yaml
services:
  app:
    image: my-app:latest
    security_opt:
      - seccomp:/path/to/profile.json
```

**Kubernetes:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  template:
    spec:
      containers:
        - name: app
          image: my-app:latest
          securityContext:
            seccompProfile:
              type: Localhost
              localhostProfile: profiles/seccomp.json
```

Kubernetes همچنین از `RuntimeDefault` پشتیبانی می‌کند که فقط از پروفایل پیش‌فرض runtime کانتینر استفاده می‌کند:

```yaml
securityContext:
  seccompProfile:
    type: RuntimeDefault
```

## فراخوانی‌های سیستمی خطرناک

بعضی syscallها در طول سال‌ها کلی vulnerability داشته‌اند:

- `ptrace()`: دیباگ کردن پردازه‌های دیگر
- `mount()`: دستکاری filesystemها
- `bpf()`: تعامل با eBPF
- `userfaultfd()`: دخیل در چندین باگ privilege escalation
- بعضی syscallهای مرتبط با namespace

این‌ها قدرتمند و برای بیشتر برنامه‌های وب غیرضروری هستند. مسدود کردنشان یک دسته کامل از تکنیک‌های پس از بهره‌برداری را حذف می‌کند.

## یک سناریوی واقعی

ابزاری به نام Snoopy وجود دارد که از eBPF برای فرار از کانتینر و privilege escalation سوءاستفاده می‌کند. مهاجمان با code execution داخل کانتینر می‌توانند از `bpf()` برای hook کردن توابع کرنل، دور زدن مکانیسم‌های امنیتی و escalation privilege استفاده کنند. اگر `bpf()` توسط seccomp بلاک شده باشد، کرنل بلافاصله درخواست را رد می‌کند.

مهاجم هنوز code execution دارد، اما نمی‌تواند آزادانه به هر interface کرنلی دسترسی پیدا کند.

به همین دلیل لایه‌ها را ترکیب می‌کنید. حذف `CAP_SYS_ADMIN` دسترسی به eBPF را محدود می‌کند. بلاک کردن syscall `bpf()` در سطح seccomp لایهٔ دوم است. حتی اگر یک لایه خراب شود، لایهٔ دیگر هست.

# AppArmor و SELinux

پس قابلیت‌ها (چه عملیات ممتازی می‌توانید انجام دهید) و seccomp (کدام syscallها را می‌توانید صدا بزنید) را پوشش دادیم. لایهٔ سوم: Linux Security Modules یا LSMs.

AppArmor و SELinux دو نمونهٔ اصلی هستند. آن‌ها به یک سؤال متفاوت جواب می‌دهند:

> حتی اگر یک پردازه capability و syscall مجاز را داشته باشد، واقعاً به چه فایل‌ها، دایرکتوری‌ها و منابع شبکه‌ای می‌تواند دسترسی داشته باشد؟

Capabilities می‌گویند چه کاری می‌توانید کنید. Seccomp می‌گوید کدام APIهای کرنل را می‌توانید صدا بزنید. LSMs می‌گویند به چه اشیایی می‌توانید دست بزنید.

## LSMs چطور کار می‌کنند

LSM یک چارچوب کرنلی است که سیاست‌های امنیتی را روی هر عملیات حساس اعمال می‌کند. وقتی یک پردازه فایل باز می‌کند، به سوکت متصل می‌شود، یا به دایرکتوری دسترسی پیدا می‌کند، LSM سیاست خودش را چک می‌کند.

AppArmor از سیاست‌های مبتنی بر مسیر استفاده می‌کند. شما می‌نویسید «این باینری می‌تواند `/etc/nginx/nginx.conf` را بخواند اما نمی‌تواند در آن بنویسد» یا «این باینری اصلاً نمی‌تواند سوکت شبکه ایجاد کند».

SELinux از سیاست‌های مبتنی بر برچسب (label) استفاده می‌کند. هر پردازه و شیء یک برچسب امنیتی می‌گیرد و سیاست مشخص می‌کند کدام پردازه‌های با چه برچسبی می‌توانند به کدام اشیای با چه برچسبی دسترسی داشته باشند. SELinux قدرتمندتر اما پیچیده‌تر است. به همین دلیل بیشتر در محیط‌های دولتی و با امنیت بالا دیده می‌شود.

## داکر چطور از LSMs استفاده می‌کند

داکر می‌تواند یک پروفایل AppArmor یا context SELinux را به پردازه‌های کانتینر متصل کند. با یک پروفایل پیش‌فرض AppArmor عرضه می‌شود که دسترسی به مسیرهای حساس هاست را محدود می‌کند. اگر AppArmor روی هاست بارگذاری شده باشد، این پروفایل به‌طور خودکار اعمال می‌شود.

پشتیبانی SELinux در دسترس است، اما نیازمند اجرای SELinux روی هاست (بیشتر در RHEL/CentOS/Fedora رایج است) و پیکربندی flag `selinux-enabled` در داکر daemon.

## چطور با هم کار می‌کنند

هر مکانیسم به یک سؤال متفاوت جواب می‌دهد:

- **Capabilities:** «چه عملیات ممتازی می‌توانم انجام دهم؟»
- **Seccomp:** «کدام APIهای کرنل را می‌توانم صدا بزنم؟»
- **LSMs:** «حتی اگر بتوانم صدا بزنم، به چه اشیایی دسترسی دارم؟»

مکمل هم هستند. یک پردازه ممکن است `CAP_NET_BIND_SERVICE` داشته باشد و seccomp ممکن است `bind()` را مجاز بداند، اما AppArmor همچنان می‌تواند آن را از اتصال به یک پورت یا interface خاص مسدود کند. هر کدام یک بعد متفاوت را محدود می‌کند.

هیچ‌کدام به تنهایی کافی نیست. اما با هم، defense in depth ایجاد می‌کنند که مهاجم برای عبور از آن باید چندین محدودیت مستقل را دور بزند.

# Rootless داکر

Rootless داکر داemon و کانتینرها را بدون دسترسی root روی هاست اجرا می‌کند. از user namespaces (همان چیزی که قبلاً بحث کردیم) استفاده می‌کند، اما فراتر می‌رود: خود داکر daemon هم به‌عنوان یک کاربر unprivileged اجرا می‌شود.

تفاوت در دامنه است. با user namespace remapping استاندارد، فقط پردازه‌های کانتینر نگاشت می‌شوند. داemon هنوز به‌عنوان root اجرا می‌شود. در rootless mode، کل زنجیره (daemon، containerd، runc) بدون root هاست اجرا می‌شود.

Rootless داکر محدودیت‌هایی دارد: نمی‌تواند به پورت‌های زیر ۱۰۲۴ متصل شود (اگرچه ابزارهایی مثل `authbind` می‌توانند دور بزنند)، پشتیبانی محدود از storage driverها، و با همهٔ network configها کار نمی‌کند.

برای محیط‌هایی که ایزوله‌سازی سطح هاست بیشتری می‌خواهند، گزینهٔ خوبی است. برای بیشتر استقرارهای تولیدی، user namespaces استاندارد به همراه سایر اقدامات مقاوم‌سازی که اینجا گفته شد حفاظت کافی می‌دهند.

# امنیت داکر Daemon

مدل امنیتی داکر فقط دربارهٔ کانتینرها نیست. خود داemon یک مرز حیاتی است.

## گروه `docker` معادل root است

در سیستم‌های دارای داکر، کاربران می‌توانند به گروه `docker` اضافه شوند تا بدون `sudo` دستورات را اجرا کنند. راحت است، اما عضویت در گروه `docker` معادل root روی هاست است.

چرا؟ کاربر در گروه `docker` می‌تواند:

- کانتینرها را با هر capabilityای شروع کند، از جمله `--privileged`
- هر دایرکتوری هاست را با دسترسی read-write کامل به کانتینر mount کند
- مستقیماً به داکر API socket دسترسی پیدا کند
- کانفیگ داکر را تغییر دهد

هر پردازه‌ای که به داکر socket دسترسی داشته باشد، عملاً دسترسی root دارد.

## مونت کردن `/var/run/docker.sock` داخل کانتینر

یک ضدالگوی رایج: mount کردن داکر socket داخل کانتینر. مردم این کار را می‌کنند تا کانتینر بتواند کانتینرهای دیگر را مدیریت کند (عوامل CI/CD، ابزارهای مانیتورینگ و...).

```yaml
services:
  container-manager:
    image: my-manager:latest
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
```

این به پردازه‌های آن کانتینر همان privileges یک عضو گروه `docker` را می‌دهد. اگر مهاجم آن کانتینر را نفوذ کند، می‌تواند کانتینرهای جدید شروع کند، filesystemهای هاست را mount کند و به دسترسی کامل سطح هاست برسد. همهٔ اینها بدون نیاز به فرار از کانتینر.

اگر نیاز به دسترسی داکر از داخل کانتینر دارید، از داکر API از طریق TLS با گواهی کلاینت یا یک proxy امن که فقط عملیات خاصی را مجاز می‌کند استفاده کنید.

# سوءاستفاده از منابع (Resource Abuse)

همهٔ حملات privilege escalation نیستند. گاهی مهاجم فقط می‌خواهد برنامه را از دسترس خارج کند.

برنامهٔ Next.js نفوذی ما را تصور کنید. به‌جای تلاش برای فرار، مهاجم یک حلقهٔ بی‌نهایت اجرا می‌کند، کلی حافظه تخصیص می‌دهد، یا هزاران پردازهٔ فرزند می‌سازد.

این حملات نیاز به privilege بالا ندارند. فقط از منابع کانتینر سوءاستفاده می‌کنند.

داکر از cgroups (Control Groups) برای محدود کردن CPU، حافظه و ایجاد پردازه استفاده می‌کند.

## محدودیت حافظه

بدون محدودیت حافظه، یک کانتینر نفوذی می‌تواند تمام RAM هاست را بخورد.

**داکر Compose:**

```yaml
services:
  nextjs:
    image: my-nextjs-app
    deploy:
      resources:
        limits:
          memory: 512M
```

**Kubernetes:**

```yaml
resources:
  requests:
    memory: "256Mi"
  limits:
    memory: "512Mi"
```

اگر پردازه از حد مجاز بگذرد، OOM killer آن را می‌کشد.

## محدودیت پردازه (`pids_limit`)

Fork bombها یک تکنیک رایج DoS هستند. یک پردازه مدام پردازه‌های فرزند می‌سازد تا جایی که سیستمعامل نمی‌تواند جدید ایجاد کند.

داکر به شما اجازه می‌دهد محدود کنید چند پردازه یک کانتینر می‌تواند بسازد.

```yaml
services:
  nextjs:
    image: my-nextjs-app
    pids_limit: 100
```

حتی با code execution، مهاجم نمی‌تواند بیش از حد مجاز پردازه ایجاد کند.

## محدودیت CPU

تخلیهٔ CPU هم یک تهدید است. محدودیت CPU تضمین می‌کند یک کانتینر نفوذی نمی‌تواند همهٔ پردازنده‌ها را بگیرد.

**داکر Compose:**

```yaml
services:
  nextjs:
    image: my-nextjs-app
    deploy:
      resources:
        limits:
          cpus: "1.0"
```

**Kubernetes:**

```yaml
resources:
  requests:
    cpu: "500m"
  limits:
    cpu: "1"
```

این محدودیت‌ها سوءاستفاده را جلوگیری نمی‌کنند، آن را مهار می‌کنند.

# دسترسی به Deviceها

پیش‌فرض، داکر کانتینرها را از سخت‌افزار هاست ایزوله می‌کند. در Linux، منابع سخت‌افزاری به‌صورت فایل در `/dev` قرار دارند. دسترسی به یکی از این‌ها معمولاً یعنی دسترسی به یک interface مدیریت‌شده توسط کرنل.

مثال‌های رایج:

- GPUهای NVIDIA برای ML/AI
- `/dev/net/tun` برای VPNهایی مثل WireGuard یا OpenVPN
- HSM برای مدیریت کلید رمزنگاری
- دستگاه‌های USB یا سریال برای صنعتی/IoT

مثلاً WireGuard به دستگاه TUN نیاز دارد:

```yaml
services:
  wireguard:
    image: linuxserver/wireguard
    devices:
      - /dev/net/tun:/dev/net/tun
    cap_add:
      - NET_ADMIN
```

به‌جای expose کردن کل `/dev` یا استفاده از `--privileged`، فقط device خاصی را که workloadتان نیاز دارد بدهید. همان اصل این مقاله: فقط چیزی را expose کنید که نیاز است، نه بیشتر.

# جمع‌بندی: دفاع در عمق

پس تمام این ویژگی‌های امنیتی داکر را جداگانه بررسی کردیم. اما قرار نیست تنها استفاده شوند. با هم کار می‌کنند.

برگردیم به مدل تهدیدمان. مهاجم از یک vulnerability در Next.js ما سوءاستفاده کرده و داخل کانتینر RCE گرفته.

حالا هر لایهٔ مقاوم‌سازی وارد عمل می‌شود:

- برنامه به‌عنوان کاربر non-root اجرا می‌شود
- همهٔ capabilities غیرضروری حذف شده‌اند
- Root filesystem read-only است
- فایل‌های موقت به tmpfs می‌روند
- Privilege escalation غیرفعال است
- محدودیت‌های CPU، حافظه و PID اعمال شده‌اند
- فقط حداقل منابع در معرض هستند

هیچ‌کدام جلوی اکسپلویت اولیه را نمی‌گیرد. اما با هم، دامنهٔ کارهایی که مهاجم می‌تواند بعد از نفوذ انجام دهد را محدود می‌کنند.

در ادامه یک نمونه پیکربندی تولیدی برای Next.js در پشت Nginx:

## `Docker`

```bash
docker network create web

docker run -d \
  --name nextjs \
  --network web \
  --user 1000:1000 \
  --read-only \
  --tmpfs /tmp \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --memory 512m \
  --cpus 1 \
  --pids-limit 100 \
  my-nextjs-app:latest

docker run -d \
  --name nginx \
  --network web \
  -p 80:80 \
  --read-only \
  --tmpfs /var/cache/nginx \
  --tmpfs /var/run \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  --security-opt no-new-privileges:true \
  nginx:latest
```

## `Docker Compose`

```yaml
services:
  nextjs:
    image: my-nextjs-app:latest
    user: "1000:1000"
    read_only: true
    tmpfs:
      - /tmp
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
    pids_limit: 100
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M

  nginx:
    image: nginx:latest
    ports:
      - "80:80"
    read_only: true
    tmpfs:
      - /var/cache/nginx
      - /var/run
    cap_drop:
      - ALL
    cap_add:
      - NET_BIND_SERVICE
    security_opt:
      - no-new-privileges:true
```

## `Kubernetes`

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nextjs
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nextjs
  template:
    metadata:
      labels:
        app: nextjs
    spec:
      containers:
        - name: nextjs
          image: my-nextjs-app:latest
          securityContext:
            runAsNonRoot: true
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop:
                - ALL
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "1"
              memory: "512Mi"
          volumeMounts:
            - name: tmp
              mountPath: /tmp
      volumes:
        - name: tmp
          emptyDir:
            medium: Memory
```

این‌ها را عیناً کپی نکنید. هر workload متفاوت است. نکته طرز فکر است: چیزهای غیرضروری را حذف کنید، فقط آنچه نیاز است expose کنید، فرض کنید برنامه روزی نفوذ خواهد شد.

# نتیجه‌گیری

امنیت داکر دفاع در عمق است، نه یک گلولهٔ نقره‌ای. Non-root users، capabilities، read-only filesystems، no-new-privileges، seccomp، LSMs، cgroups، محدودیت device. هر کدام یک تکه از سطح حمله را حذف می‌کنند. به تنهایی مفیدند، با هم پس از بهره‌برداری را خیلی سخت‌تر می‌کنند.

داکر جلوی نفوذ به برنامه را نمی‌گیرد. کاری که می‌کند محدود کردن کارهایی است که مهاجم بعد از ورود می‌تواند انجام دهد. و این تفاوت مهمی است. هر permission غیرضروری، دایرکتوری writable یا device در معرض، فرصتی است که لازم نبود به مهاجم بدهید.

امنیت به معنی غیرممکن کردن نفوذ نیست. امنیت یعنی وقتی نفوذ اتفاق می‌افتد، مهاجم تا حد ممکن گزینه‌های کمی داشته باشد.
