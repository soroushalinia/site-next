# مقدمه

امنیت کانتینر دهه اخیر خیلی پیشرفت کرده، اما توصیه‌هایی که می‌شه همچنان قدیمی‌ست.

اگه بهترین شیوه‌های امنیتی داکر رو جستجو کنید، به اینا برمی‌خورید:
- به عنوان کاربر روت اجرا نکنید.
- از فایل‌سیستم read-only استفاده کنید.
- seccomp رو فعال کنید.
- کانتینر رو پریمیوم اجرا نکنید.

این توصیه‌ها درست هستند و باید رعایت بشن. ولی معمولاً به عنوان یه قانون خشک مطرح می‌شن، نه یه مفهومی که بشه درکش کرد.

یکی از منابع مورد علاقه من، [چیت‌شیت امنیت داکر از OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html) است. پیشنهادهای عالی داره، اما هیچوقت توضیح نمی‌ده چرا این کارها لازم هستند و جلوی چه حملاتی رو می‌گیرن. این نوشته روی همان چیت‌شیت ساخته شده با این تفاوت که سازوکارهای امنیتی لینوکس پشت این پیشنهادها و نحوه جلوگیری از حملات رو توضیح می‌ده. آخرش می‌فهمید هر گزینه چرا مهمه و کجا باید استفاده بشه.

# مدل تهدید

قبل از اینکه بریم سراغ ویژگی‌ها، یه سوال رو باید جواب بدیم:

> داریم از کی دفاع می‌کنیم؟

توصیه‌های امنیتی فقط تو بستر یه مدل تهدید معنا دارن. کانتینری که روی ماشین توسعه اجرا می‌شه با یه API پروداکشن که تو دسترس عموم هست فرق داره.

بقیه نوشته رو با این سناریو پیش می‌ریم:
- اپلیکیشن داخل کانتینر تو محیط پروداکشن اجرا می‌شه.
- اپلیکیشن در معرض یه کاربر غیرقابل اعتماد از طریق شبکه‌ست.
- مهاجم به خاطر یه vulnerability توی برنامه، به RCE (اجرای کد از راه دور) داخل کانتینر رسیده.
- مهاجم هر دستوری می‌تونه با دسترسی پردازه اپلیکیشن اجرا کنه.

اینجا مشکل این نیست که داکر کارش رو درست انجام نداده. بلکه ویژگی‌های امنیتی داکر بعد از نفوذ خودشون رو نشون می‌دن. جلوگیری از SQL injection، command injection یا deserialization وظیفه داکر نیست. اون با توسعه‌دهنده‌ست.

هدف مهاجم می‌تونه اینا باشه:
- خوندن داده‌های حساس مثل کلید API، کدوم راز و رمز اپلیکیشن.
- تغییر اپلیکیشن یا تنظیماتش.
- موندگاری تو سیستم بعد از ری‌استارت کانتینر.
- بالا بردن دسترسی تو کانتینر.
- فرار از کانتینر و زدن هاست.
- دسترسی به کانتینرهای دیگه تو شبکه.
- مصرف منابع و DoS زدن.

هدف این ویژگی‌ها اینه که مهاجم رو بعد از نفوذ محدود کنن. هرکدوم از این کارها باید سخت یا حتی غیرممکن باشه.

## مثال واقعی

هر سال vulnerabilityهای RCE تو اپلیکیشن‌های کانتینرشده پیدا می‌شه. مثلاً vulnerability کامپوننت سرور React تو ۲۰۲۵ ([CVE-2025-55182](https://nvd.nist.gov/vuln/detail/CVE-2025-55182)). مال خود React بود ولی اپلیکیشن‌های Next.js رو زد و مهاجما می‌تونستن با یه درخواست HTTP کد دلخواه روی سرور اجرا کنن.

حالا تصور کنید اپ شما تو یه کانتینر داکره و از Next.js وصله‌نخورده استفاده می‌کنه. مهاجم می‌تونه کد مخرب تو کانتینر شما اجرا کنه.

حالا بپرسید:
- می‌تونن اپ شما رو عوض کنن؟
- می‌تونن secrets مانت شده رو بدزدن؟
- می‌تونن تو سیستم باقی بمونن؟
- می‌تونن به کانتینرهای دیگه دسترسی پیدا کنن؟
- می‌تونن به هاست فرار کنن؟
- می‌تونن منابع هاست رو ببلعن؟

ایناس که ویژگی‌های امنیتی داکر تو این نوشته پاسخ می‌دن.

در این زنجیره، داکر از لایه `Engine` تا `Container` رو مدیریت می‌کنه: چرخه حیات کانتینرها، namespaceها، capabilityها، پروفایل seccomp، LSMها و cgroupها.

**چیزی که داکر فراهم نمی‌کنه یه مرز امنیتی در برابر کرنل لینوکسه.** کرنل بین همه کانتینرهای یه هاست مشترکه. داکر سازوکارهای امنیتی کرنل رو تنظیم می‌کنه ولی لایه جدید اضافه نمی‌کنه.

اگه یه vulnerability تو یه زیرسیستم کرنل مثل `OverlayFS`، `eBPF` یا `io_uring` باشه، مهاجم می‌تونه ایزوله داکر رو دور بزنه. اینا باگ کرنل هستن، نه مشکل پیکربندی داکر. مثالش [CVE-2023-0386](https://nvd.nist.gov/vuln/detail/CVE-2023-0386) که یه فرار از کانتینر بود با سوءاستفاده از OverlayFS.

این به معنی ناامن بودن داکر نیست. یعنی امنیت کانتینر همون امنیت لینوکسه. تو این نوشته درباره mitigationهایی حرف می‌زنیم که تأثیر کانتینرهای نفوذی رو کم می‌کنن.

# اجرای کانتینر به عنوان کاربر غیرروت

احتمالاً رایج‌ترین توصیه امنیتی برای داکر اینه که کانتینرتون رو به عنوان روت اجرا نکنید. توصیه خوبیه ولی خیلی‌ها درکش نمی‌کنن. سوال اینجاست: اگه کانتینرها ایزوله هستن، پس چرا فرق می‌کنه روت باشه یا نه؟

پاسخ کوتاه: روت کانتینر با روت هاست یکی نیست، ولی همچنان از یه کاربر معمولی تو کانتینر قدرت بیشتری داره.

## روت داخل کانتینر با روت هاست یکی نیست

تو یه سیستم لینوکس معمولی، کاربر روت UID 0 هست و به همه جا دسترسی داره. ولی مدل امنیتی کانتینرها فرق می‌کنه. UID 0 داخل کانتینر یعنی کاربر فقط تو namespace همون کانتینر روت محسوب می‌شه، نه هاست.

مثلاً یه پردازه روت داخل داکر نمی‌تونه این کارها رو بکنه:
- ماژول کرنل بارگذاری کنه
- هر فایل‌سیستمی رو مانت کنه
- پارامترهای کرنل رو عوض کنه
- ساعت سیستم رو تغییر بده
- پردازه‌های بیرون کانتینر یا هاست رو ببینه یا کنترل کنه

این کارها نیاز به capabilityهایی دارن که داکر عمداً از کاربر روت تو کانتینر گرفته. ولی با همه این محدودیت‌ها، بازم روت تو کانتینر قدرتمندترین کاربرهاست.

## چرا Kubernetes می‌گه `runAsNonRoot`

اگه تا حالا رو Kubernetes کاری کرده باشید، این رو دیدید:

```yaml
securityContext:
	runAsNonRoot: true
```

این به Kubelet می‌گه مطمئن شو کانتینر با UID 0 شروع نشه. اگه ایمیج طوری باشه که به عنوان روت اجرا بشه، Kubernetes از شروع کانتینر جلوگیری می‌کنه. دلیلش این نیست که Kubernetes به ایزوله داکر اعتماد نداره. بیشتر اپلیکیشن‌ها اصلاً نیازی به دسترسی روت ندارن برای HTTP سرویس دادن یا کار با دیتابیس.

## فرار از کانتینر

گاهی vulnerability تو کرنل باعث می‌شه مهاجم بتونه از کانتینر به هاست فرار کنه. معروف‌ترینش [CVE-2019-5736](https://unit42.paloaltonetworks.com/breaking-docker-via-runc-explaining-cve-2019-5736/) بود که با عوض کردن باینری runC روی هاست، از کانتینر فرار می‌کرد.

توجه کنید که اجرا به عنوان کاربر غیرروت جلوی فرار رو نمی‌گیره، ولی سطح حمله رو کم می‌کنه و کار مهاجم رو سخت‌تر می‌کنه.

## User Namespace

قبلاً گفتیم روت داخل کانتینر با روت هاست فرق داره. این جداسازی با یه ویژگی تو کرنل به نام user namespace ممکن شده. این ویژگی UID و GID رو بین کانتینر و هاست نگاشت می‌کنه. مثلاً یه پردازه با UID 0 داخل کانتینر، روی هاست UID 100000 حساب می‌شه.

نحوه نگاشت:

| داخل کانتینر | روی هاست |
| -------------------- | ----------- |
| UID 0 (روت) | UID 100000 |
| UID 1 | UID 100001 |
| UID 1000 | UID 101000 |

یعنی حتی اگه روت کانتینر بخواد به فایلی دسترسی پیدا کنه که مال روت هاسته، نمی‌تونه چون از دید کرنل اون کاربر روت نیست.

User namespaceها قدرتمند هستن ولی تو خیلی از نصب‌های داکر پیش‌فرض فعال نیستن. دلیلش سازگاریه: bind mountها، نگاشت ownership فایل و بعضی storage backendها وقتی UIDها رمپ می‌شن فرق می‌کنن. بعضی ایمیج‌ها فرض می‌کنن می‌تونن به عنوان روت فایل بنویسن و اون فایل رو هاست هم مال روت باشه، که با user namespace رمپ خراب می‌شه. این مشکلات قابل حل هستن ولی نیاز به تست و پیکربندی داره.

برای پروداکشن‌های با امنیت بالا، فعال کردن user namespace باید اولویت باشه. حفاظتی که در برابر فرار از کانتینر می‌ده به سختی با هیچ سازوکار دیگه‌ای قابل دستیابیه.

# Linux Capabilities

اگه اجرا به عنوان کاربر غیرروت قدم اوله، capabilities قدم دومه.

حتی اگه اپ شما به عنوان روت تو کانتینر اجرا بشه، بازم قدرت روت لینوکس سنتی رو نداره. چون لینوکس مدرن دیگه روت رو همه-یا-هیچ نمی‌بینه. عملیات ممتاز رو به capabilityهای مجزا تقسیم کرده.

## چرا لینوکس روت رو تیکه‌تیکه کرد

قبلاً یونیکس فقط دو سطح داشت: یا روت (UID 0) با دسترسی همه‌جا، یا کاربر معمولی با کلی محدودیت. ساده بود ولی زیادی درشت بود. Nginx رو در نظر بگیرید. می‌خواد به پورت ۸۰ وصل بشه، نیاز به روت داره. ولی به همه قدرت روت نیاز نداره. ماژول کرنل بارگذاری کنه؟ نه. سیستم رو reboot کنه؟ نه.

Capabilities راه‌حل اینن. قدرت روت رو می‌شکنن به مجوزهای ریز. هرکدوم اجازه یه عملیات خاص می‌ده.

چندتا capability معروف:

| Capability | اجازه |
| ---------------------- | ---------------------------------------------------------------------- |
| `CAP_NET_BIND_SERVICE` | اتصال به پورت زیر ۱۰۲۴ |
| `CAP_NET_ADMIN` | تنظیم شبکه، مسیریابی، فایروال |
| `CAP_SYS_PTRACE` | ردیابی و دیباگ پردازه‌های دیگه |
| `CAP_SYS_MODULE` | بارگذاری ماژول کرنل |
| `CAP_SYS_TIME` | تغییر ساعت سیستم |
| `CAP_SYS_ADMIN` | کلی عملیات مدیریتی متنوع |

## مجموعه capability پیش‌فرض داکر

وقتی کانتینر رو شروع می‌کنید، داکر خودش بعضی capabilityهای خطرناک رو حذف کرده. با این دستور می‌تونید ببینید چه capabilityهایی تو کانتینر فعاله:

```bash
docker run --rm alpine sh -c "
apk add --no-cache libcap >/dev/null
capsh --print
"
```

خروجی:

![capabilities پیش‌فرض](/images/blog/docker-security-under-the-hood/default-docker-capabilities.png)

می‌بینید که `CAP_SYS_MODULE`، `CAP_SYS_BOOT`، `CAP_SYS_ADMIN` و `CAP_SYS_TIME` وجود ندارن. به همین دلیله که روت تو کانتینر پیش‌فرض داکر نمی‌تونه کلی کار رو بکنه.

## افزودن capability با `--cap-add`

فرض کنید Nginx رو دارید و می‌خواید به پورت ۸۰ وصل بشه. به جای دادن همه دسترسی‌ها:

```bash
docker run \
--cap-drop ALL \
--cap-add NET_BIND_SERVICE \
nginx
```

این خیلی امن‌تر از اینه که همه capabilityها رو فعال کنید.

## چرا `CAP_SYS_ADMIN` همون روت جدیده

`CAP_SYS_ADMIN` یه capability خاصه. برخلاف بقیه که یه کار خاص رو اجازه می‌دن، این یکی کلی عملیات مدیریتی رو اجازه می‌ده که ربطی به هم ندارن. مثلاً:

- مانت فایل‌سیستم
- عملیات namespace
- تنظیم بعضی رابط‌های کرنل
- عملیات فایل سیستمی ممتاز
- کار با eBPF (بسته به نسخه کرنل)

خیلی از فرارهای کانتینر سعی می‌کنن این capability رو به دست بیارن. اگه اپ شما نیاز نداره، اضافه نکنید.

## `CAP_NET_ADMIN`: از اسمش قوی‌تره

`CAP_NET_ADMIN` فقط مدیریت شبکه نیست. با این capability می‌تونید:
- interface شبکه بسازید یا تغییر بدید
- جدول مسیریابی تنظیم کنید
- فایروال مدیریت کنید
- packet forwarding فعال کنید
- namespace شبکه رو عوض کنید
- traffic control (tc) بزنید

اگه سرور VPN یا CNI plugin اجرا می‌کنید، بله. برای یه وب اپ که فقط HTTP سرویس می‌ده؟ نه. دادنش به اپ فقط به مهاجم گزینه بیشتر می‌ده.

## مثال

فرض کنید Next.js می‌خواید پروداکشن بدید. معمولاً Next.js پورت ۸۰ رو مستقیم باز نمی‌کنه، روی ۳۰۰۰ گوش می‌ده و یه reverse proxy (Nginx, Traefik) بقیه کار رو می‌کنه. تو این حالت، اپ اصلاً به هیچ capabilityای نیاز نداره.

**Docker Compose:**
```yaml
services:
  nextjs:
    image: my-nextjs-app:latest
    cap_drop:
      - ALL
```

**Kubernetes:**
```yaml
securityContext:
  capabilities:
    drop:
      - ALL
```

حالا اگه مهاجم از اون vulnerability Next.js استفاده کنه و بیاد تو کانتینر، نمی‌تونه کار ممتاز بکنه. چون capabilityها رو ندادیم.

اگه اپ روی پورت ۸۰ گوش می‌ده (مثل Nginx)، به `NET_BIND_SERVICE` نیاز داره. فقط همون رو بدید:

**Docker Compose:**
```yaml
services:
  nginx:
    image: nginx:latest
    cap_drop:
      - ALL
    cap_add:
      - NET_BIND_SERVICE
```

**Kubernetes:**
```yaml
securityContext:
  capabilities:
    drop:
      - ALL
    add:
      - NET_BIND_SERVICE
```

فرقی نمی‌کنه Next.js باشه یا Nginx یا هر چیز دیگه. فقط چیزی رو بدید که اپ نیاز داره.

# کانتینر پریمیوم (Privileged)

`--privileged` یه پرچمه که می‌گه «همه چیز رو بده». داکر همه capabilityها رو می‌ده، دسترسی به deviceهای هاست رو باز می‌کنه و کلی سازوکار ایمنی رو غیرفعال می‌کنه. کانتینر عملاً مثل یه پردازه عادی روی هاست می‌شه. متأسفانه خیلی‌ها به عنوان راه‌حل موقتی استفاده می‌کنن: یه چیزی کار نمی‌کنه، `--privileged` می‌زنند و درست می‌شه. ولی این سمه. اگه یه جایی گیر کردید، ببینید واقعاً به چی نیاز دارید: یه capability خاص؟ دسترسی به یه device؟ `--privileged` رو بذارید واسه کارهای زیرساختی سطح پایین، نه وب اپ و API شما.

# فایل‌سیستم read-only

پیش‌فرض کانتینر، فایل‌سیستم ریشه‌ش قابل نوشتنه. هر پردازه‌ای داخلش می‌تونه فایل ایجاد کنه، تغییر بده یا پاک کنه. برای خیلی از اپ‌ها این لازم نیست. یه وب‌سرور کد رو می‌خونه، درخواست جواب می‌ده، شاید لاگ یا کش بزنه. به ندرت پیش میاد بخواد باینری خودش رو عوض کنه.

داکر می‌ذاره فایل‌سیستم ریشه رو read-only مانت کنید:

**Docker:** `docker run --read-only nginx`

**Docker Compose:**
```yaml
services:
  app:
    image: my-app:latest
    read_only: true
```

**Kubernetes:**
```yaml
securityContext:
  readOnlyRootFilesystem: true
```

وقتی مهاجم بیاد تو کانتینر، اولین کارش اینه که ببینه می‌تونه موندگار بشه. با فایل‌سیستم read-only نمی‌تونه باینری رو عوض کنه، وب شل بذاره، بدافزار دانلود کنه یا cron job نصب کنه.

## tmpfs برای فضای موقت

خوب، بیشتر اپ‌ها یه جایی برای نوشتن موقت نیاز دارن. مثل `/tmp`، سوکت، PID file، آپلود، کش. به جای اینکه کل فایل‌سیستم رو writable کنید، می‌تونید مسیرهای خاص رو tmpfs (تو حافظه) بزنید:

**Docker:** `docker run --read-only --tmpfs /tmp my-nextjs-app:latest`

**Docker Compose:**
```yaml
services:
  nextjs:
    image: my-nextjs-app:latest
    read_only: true
    tmpfs:
      - /tmp
```

**Kubernetes:**
```yaml
volumes:
  - name: tmp
    emptyDir:
      medium: Memory
containers:
  - name: nextjs
    volumeMounts:
      - name: tmp
        mountPath: /tmp
```

tmpfs تو حافظه‌ست. هر چی بنویسید با توقف کانتینر پاک می‌شه. اپ فضای موقت داره ولی تغییر دائمی نمی‌تونه بکنه.

## مسیرهای قابل نوشتن باید صریح باشند

یکی از مزایای بزرگ سیستم فایل فقط‌خواندنی این است که شما را مجبور به فکر کردن می‌کند. اپ من واقعاً کجا نیاز به نوشتن دارد؟ به جای اجازه نوشتن در همه جا، چند مکان معدود را که نیاز دارد تعریف می‌کنید.

مثلاً:
- `/tmp` برای فایل‌های موقت.
- `/var/log` اگر لاگ روی دیسک نوشته می‌شود.
- `/uploads` برای محتوای آپلودشده توسط کاربر.

بقیه چیزها تغییرناپذیر می‌مانند. این سطح حمله را به میزان قابل توجهی کاهش می‌دهد.

## read-only چی رو نمی‌گیره؟

read-only جلوی اکسپلویت اولیه رو نمی‌گیره. جلوی اجرای کد رو نمی‌گیره. فقط کارهای بعد از نفوذ رو محدود می‌کنه.

یه نکته مهم: مهاجم می‌تونه از `/dev/shm` استفاده کنه، که یه فایل‌سیستم تو حافظه‌ست، بدافزار رو اونجا بریزه و اجرا کنه بدون اینکه اثری رو دیسک بمونه. به این می‌گن fileless malware و read-only رو دور می‌زنه. [Sysdig این رو مستند کرده](https://www.sysdig.com/blog/containers-read-only-fileless-malware).

به همین دلیل read-only فقط یه لایه‌ست. باید با drop capability، seccomp و no-new-privileges ترکیبش کنید. defense in depth.

## کانتینر read-only و زیرساخت تغییرناپذیر

این ایده با immutable infrastructure هماهنگه. تو یه سیستم تغییرناپذیر، هیچوقت workload در حال اجرا رو درجا عوض نمی‌کنید. اپ نیاز به آپدیت داره؟ ایمیج جدید بسازید، کانتینر جدید بدید. نه SSH و نه ویرایش فایل. کانتینر نفوذی شد؟ پاکش کنید و یه تازه از یه ایمیج معتبر راه بندازید. فایل‌سیستم read-only این رو اعمال می‌کنه.

# جلوگیری از افزایش دسترسی با no-new-privileges

تا اینجا درباره کاهش قدرت اولیه حرف زدیم. ولی اگه پردازه بعد از شروع سعی کنه قدرت بیشتری بگیره چی؟

تو لینوکس دو راه رایج داره: باینری‌های setuid و file capabilities. کرنل یه ویژگی داره به اسم No New Privileges (NNP) که جلوی این رو می‌گیره.

**Docker:** `docker run --security-opt no-new-privileges:true my-app:latest`

**Docker Compose:**
```yaml
services:
  app:
    image: my-app:latest
    security_opt:
      - no-new-privileges:true
```

**Kubernetes:**
```yaml
securityContext:
  allowPrivilegeEscalation: false
```

با فعال بودنش، کرنل تضمین می‌کنه پردازه نمی‌تونه قدرتی که نداره رو به دست بیاره. فرقی نمی‌کنه چه اجرایی رو اجرا کنه. این یکی از ساده‌ترین و مؤثرترین کارهای ممکنه.

# Seccomp: محدود کردن فراخوانی‌های سیستمی

حتی بعد از drop capability و جلوگیری از افزایش دسترسی، یه پردازه نفوذی همچنان می‌تونه syscall (فراخوانی سیستمی) بزنه. هر چی اپ تو userspace با کرنل انجام بده از طریق syscall می‌ره: خوندن فایل، باز کردن سوکت، ایجاد پردازه، تخصیص حافظه. همه چی.

Seccomp به شما کنترل می‌ده کدوم syscallها رو یه پردازه بتونه بزنه. لینوکس مدرن صدها syscall داره. `mount()`، `bpf()`، `ptrace()`، کلی interface قدرتمند که بیشتر اپ‌ها هیچوقت استفاده نمی‌کنن.

## پروفایل پیش‌فرض seccomp داکر

داکر پیش‌فرض یه پروفایل seccomp به هر کانتینر اعمال می‌کنه. syscallهای پرخطر که اپ معمولی نیاز نداره رو بلاک می‌کنه. ولی این پروفایل عمداً宽松 (permissive) است. چیزهای واضحاً خطرناک رو بلاک می‌کنه ولی یه whitelist سفت‌وسخت نیست. چون stricter کردنش باعث می‌شه کلی چیز بشکنه.

برای محیط‌های با امنیت بالا، پروفایل پیش‌فرض رو به عنوان نقطه شروع ببینید، نه آخر خط. پروفایل سفارشی که فقط syscallهای مورد نیاز اپ رو اجازه بده خیلی قوی‌تره.

## چطور seccomp رو پیکربندی کنیم

داکر با `--security-opt` پروفایل سفارشی قبول می‌کنه:

```bash
docker run --security-opt seccomp=/path/to/profile.json my-app
```

پروفایل یه فایل JSON که مشخص می‌کنه کدوم syscallها مجاز یا ممنوع. با `unconfined` هم می‌تونید seccomp رو بطور کلی غیرفعال کنید (توصیه نمی‌شه).

برای پروفایل سفارشی، با `strace` یا `auditd` ضبط کنید اپ شما تو کار معمولی چه syscallهایی می‌زنه، بعد ازش whitelist بسازید. مستندات رسمی داکر [اینجا](https://docs.docker.com/engine/security/seccomp/) فرمت و مثال داره.

**Docker Compose:**
```yaml
services:
  app:
    image: my-app:latest
    security_opt:
      - seccomp:/path/to/profile.json
```

**Kubernetes:**
```yaml
securityContext:
  seccompProfile:
    type: Localhost
    localhostProfile: profiles/seccomp.json
```

یا `RuntimeDefault` که فقط پروفایل پیش‌فرض runtime رو استفاده کنه:
```yaml
securityContext:
  seccompProfile:
    type: RuntimeDefault
```

## syscallهای خطرناک

بعضی syscallها توی کلی vulnerability نقش داشتن:
- `ptrace()`: دیباگ پردازه‌های دیگه
- `mount()`: دستکاری فایل‌سیستم
- `bpf()`: کار با eBPF
- `userfaultfd()`: کلی باگ افزایش دسترسی
- بعضی syscallهای مرتبط با namespace

اینها برای بیشتر وب اپ‌ها غیرضروری و قدرتمند هستن. بلاک کردنشون یه دسته کامل از تکنیک‌های بعد از نفوذ رو حذف می‌کنه.

## مثال واقعی

ابزاری به اسم Snoopy هست که از eBPF برای فرار از کانتینر و افزایش دسترسی استفاده می‌کنه. اگه `bpf()` توسط seccomp بلاک شده باشه، کرنل درخواست رو رد می‌کنه. مهاجم هنوز اجرای کد داره ولی نمی‌تونه بره تو هر interface کرنلی.

به همین دلیله که لایه‌ها رو ترکیب می‌کنید. `CAP_SYS_ADMIN` رو حذف می‌کنید، `bpf()` رو تو seccomp بلاک می‌کنید. حتی اگه یه لایه شکست بخوره، لایه دیگه هست.

# AppArmor و SELinux

تا اینجا capabilities (چه کار ممتازی می‌تونید بکنید) و seccomp (چه syscallهایی می‌تونید بزنید) رو گفتیم. لایه سوم LSMs (Linux Security Modules) هست. AppArmor و SELinux دو مدل اصلیش.

اینارو یه سوال دیگه جواب می‌دن:

> حتی اگه یه پردازه capability و syscall مجاز رو داشته باشه، واقعاً به چه فایل‌ها و منابع شبکه‌ای می‌تونه دسترسی داشته باشه؟

Capabilities می‌گن چی می‌تونید بکنید. Seccomp می‌گه کدوم API کرنل رو می‌تونید صدا بزنید. LSMs می‌گن به کدوم اشیا می‌تونید دست بزنید.

AppArmor با مسیر کار می‌کنه: «این باینری می‌تونه `/etc/nginx/nginx.conf` رو بخونه ولی توش ننویسه». SELinux با برچسب: هر پردازه و شیء یه برچسب امنیتی داره. SELinux قدرتمندتر ولی پیچیده‌تر.

داکر با یه پروفایل پیش‌فرض AppArmor میاد که دسترسی به مسیرهای حساس هاست رو محدود می‌کنه. SELinux اگه هاست روش فعال باشه (معمولاً RHEL/CentOS/Fedora) قابل استفاده‌ست.

هرکدوم یه بعد رو محدود می‌کنه. هیچکدوم تنها کافی نیستن. با هم defense in depth ایجاد می‌کنن.

# Rootless Docker

Rootless Docker دیمون و کانتینرها رو بدون دسترسی روت روی هاست اجرا می‌کنه. از همون user namespace استفاده می‌کنه ولی فراتر می‌ره: خود دیمون داکر هم به عنوان یه کاربر بدون امتیاز اجرا می‌شه.

تو user namespace معمولی فقط پردازه‌های کانتینر رمپ می‌شن، ولی دیمون still روت می‌مونه. تو rootless mode، کل زنجیره (دیمون، containerd، runc) بدون روت اجرا می‌شن.

محدودیت داره: نمی‌تونه به پورت زیر ۱۰۲۴ وصل بشه (مگر با `authbind`)، درایور ذخیره‌سازی محدود و با همه تنظیمات شبکه جواب نمی‌ده. برای محیط‌هایی که ایزوله بیشتری می‌خوان خوبه. برای پروداکشن معمولی، user namespace استاندارد با بقیه کارایی که گفتیم کافیه.

# امنیت دیمون داکر

مدل امنیتی داکر فقط کانتینرها نیست. خود دیمون یه مرز حیاتیه.

## گروه `docker` == روت

توی سیستم‌هایی که داکر دارن، کاربرا رو به گروه `docker` اضافه می‌کنن تا بدون `sudo` دستور بدن. راحته ولی عضویت در گروه `docker` یعنی دسترسی روت روی هاست.

چرا؟ چون کسی که تو گروه `docker` هست می‌تونه:
- کانتینر با هر capabilityای از جمله `--privileged` راه بندازه
- هر دایرکتوری هاست رو با دسترسی read-write به کانتینر مانت کنه
- مستقیم بره سراغ سوکت API داکر
- تنظیمات داکر رو عوض کنه

هر پردازه‌ای که به سوکت داکر دسترسی داشته باشه عملاً روت داره.

## مانت `/var/run/docker.sock` تو کانتینر

یه anti-pattern رایج: سوکت داکر رو می‌ریزن تو کانتینر تا کانتینر بتونه بقیه کانتینرها رو مدیریت کنه (مثل CI/CD agents).

```yaml
services:
  container-manager:
    image: my-manager:latest
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
```

این یعنی کانتینر قدرت گروه `docker` رو داره. اگه مهاجم بیاد تو این کانتینر، می‌تونه کانتینر جدید بندازه، فایل‌سیستم هاست رو مانت کنه و برسه به هاست. بدون اینکه حتی از کانتینر فرار کنه.

اگه به دسترسی داکر از داخل کانتینر نیاز دارید، از API داکر با TLS و گواهی یا یه proxy امن که فقط عملیات خاصی رو اجازه می‌ده استفاده کنید.

# سوءاستفاده از منابع

همه حمله‌ها برای افزایش دسترسی نیست. بعضی وقتا مهاجم فقط می‌خواد اپتو از دسترس خارج کنه.

اپ Next.js نفوذی رو تصور کنید. به جای فرار، یه حلقه بی‌نهایت می‌زنه، حافظه می‌بلع یا هزاران پردازه بچه درست می‌کنه. این حملات به قدرت خاصی نیاز ندارن. فقط منابع رو می‌خورن.

داکر با cgroups محدودیت CPU، حافظه و تعداد پردازه می‌ذاره.

## محدودیت حافظه

بدون محدودیت حافظه، یه کانتینر نفوذی می‌تونه همه RAM هاست رو بخوره.

**Docker Compose:**

```yaml
services:
  nextjs:
    image: my-nextjs-app
    deploy:
      resources:
        limits:
          memory: 512M
```

**Kubernetes:**

```yaml
resources:
  requests:
    memory: "256Mi"
  limits:
    memory: "512Mi"
```

اگر پردازه از حد مجاز فراتر رود، OOM killer آن را خاتمه می‌دهد.

## محدودیت پردازه (`pids_limit`)

Fork bomb یه تکنیک DoS: یه پردازه هی بچه درست می‌کنه تا سیستم دیگه نتونه جدید بسازه.

داکر محدودیت تعداد پردازه داره:

```yaml
services:
  nextjs:
    image: my-nextjs-app
    pids_limit: 100
```

حتی با اجرای کد، مهاجم نمی‌تواند بیش از حد مجاز پردازه ایجاد کند.

## محدودیت CPU

یه کانتینر نفوذی می‌تونه همه CPU رو قورت بده.

**Docker Compose:**

```yaml
services:
  nextjs:
    image: my-nextjs-app
    deploy:
      resources:
        limits:
          cpus: "1.0"
```

**Kubernetes:**

```yaml
resources:
  requests:
    cpu: "500m"
  limits:
    cpu: "1"
```

این محدودیت‌ها از سوءاستفاده جلوگیری نمی‌کنن، مهارش می‌کنن.

# دسترسی به دستگاه‌ها

پیش‌فرض داکر کانتینرها رو از سخت‌افزار هاست ایزوله می‌کنه. تو لینوکس، منابع سخت‌افزاری به صورت فایل تو `/dev` هستن. دسترسی به یکی از اینا یعنی دسترسی به یه interface کرنلی.

مثال‌های رایج:
- GPUهای NVIDIA برای ML/AI
- `/dev/net/tun` برای VPNهایی مثل WireGuard
- HSM برای مدیریت کلید رمز
- دستگاه USB یا سریال برای IoT

WireGuard مثلاً نیاز به TUN داره:

```yaml
services:
  wireguard:
    image: linuxserver/wireguard
    devices:
      - /dev/net/tun:/dev/net/tun
    cap_add:
      - NET_ADMIN
```

به جای در معرض گذاشتن کل `/dev` یا `--privileged`، فقط همون دستگاه خاص رو بدید. همون اصل: فقط چیزی که نیازه.

# جمع‌بندی

همه این ویژگی‌ها رو جدا جدا گفتیم ولی قرار نیست تنها استفاده بشن. با هم کار می‌کنن.

برگردیم به مدل تهدید. مهاجم از یه vulnerability تو Next.js استفاده می‌کنه و RCE می‌گیره. حالا هر لایه دفاعی وارد عمل می‌شه:
- اپ به عنوان کاربر غیرروت اجرا می‌شه
- همه capabilityهای غیرضروری حذف شدن
- فایل‌سیستم ریشه read-only
- فایل موقت می‌ره رو tmpfs
- افزایش دسترسی غیرفعاله
- CPU، حافظه و PID محدود شده
- فقط حداقل منابع در معرض

هیچکدوم جلوی نفوذ اولیه رو نمی‌گیره. ولی با هم، کارایی که مهاجم می‌تونه بعد از ورود بکنه رو محدود می‌کنن.

این یه نمونه تنظیمات برای Next.js پشت Nginx:

## `Docker`

```bash
docker network create web

docker run -d \
  --name nextjs \
  --network web \
  --user 1000:1000 \
  --read-only \
  --tmpfs /tmp \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --memory 512m \
  --cpus 1 \
  --pids-limit 100 \
  my-nextjs-app:latest

docker run -d \
  --name nginx \
  --network web \
  -p 80:80 \
  --read-only \
  --tmpfs /var/cache/nginx \
  --tmpfs /var/run \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  --security-opt no-new-privileges:true \
  nginx:latest
```

## `Docker Compose`

```yaml
services:
  nextjs:
    image: my-nextjs-app:latest
    user: "1000:1000"
    read_only: true
    tmpfs:
      - /tmp
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
    pids_limit: 100
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M

  nginx:
    image: nginx:latest
    ports:
      - "80:80"
    read_only: true
    tmpfs:
      - /var/cache/nginx
      - /var/run
    cap_drop:
      - ALL
    cap_add:
      - NET_BIND_SERVICE
    security_opt:
      - no-new-privileges:true
```

## `Kubernetes`

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nextjs
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nextjs
  template:
    metadata:
      labels:
        app: nextjs
    spec:
      containers:
        - name: nextjs
          image: my-nextjs-app:latest
          securityContext:
            runAsNonRoot: true
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop:
                - ALL
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "1"
              memory: "512Mi"
          volumeMounts:
            - name: tmp
              mountPath: /tmp
      volumes:
        - name: tmp
          emptyDir:
            medium: Memory
```

اینارو عیناً کپی نکنید. هر workload فرق داره. نکته مهم طرز فکره: چیزی که نیاز ندارید رو حذف کنید، فقط چیزی که لازمه رو بدید، فرض کنید اپ یه روز نفوذی می‌شه.

# نتیجه‌گیری

امنیت داکر defense in depthe، نه یه گلوله نقره‌ای. کاربر غیرروت، capabilities، فایل‌سیستم read-only، no-new-privileges، seccomp، LSMها، cgroups، محدودیت device. هرکدوم یه تیکه از سطح حمله رو برمی‌داره. تنها مفید هستن، با هم کار بعد از نفوذ رو خیلی سخت‌تر می‌کنن.

داکر جلوی نفوذ به اپ شما رو نمی‌گیره. کاری که می‌کنه محدود کردن کارهایی‌ست که مهاجم بعد از ورود می‌تونه بکنه. این تفاوت مهمیه. هر مجوز اضافی، دایرکتوری قابل نوشتن یا device در معرض، یه فرصته که لازم نبوده به مهاجم بدید.

امنیت درباره غیرممکن کردن نفوذ نیست. درباره اینه که مطمئن بشید وقتی نفوذ اتفاق می‌افته، مهاجم تا حد ممکن گزینه کم داشته باشه.
